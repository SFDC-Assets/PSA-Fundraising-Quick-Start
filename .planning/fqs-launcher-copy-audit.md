# FQS Gift Entry Single Launcher — Copy Audit (G7.5)

**Target flow:** `force-app/main/default/flows/FQS_Gift_Entry_Single_Launcher_Account.flow-meta.xml`
**Audit date:** 2026-07-26
**Status:** G7.5.a copy edits applied 2026-07-28 (deploy pending). G7.5.b (wizard purge) + G7.5.c (dead choice removal) still queued.
**Audience:** New FQS users, self-serve — labels stand alone, helpText fills the "when do I use this" gap.

## 2026-07-28 departure from the audit — Section 12 rows 90 / 91

Rows 90/91 (`dtNextTransactionDate` field + helpText) originally marked "no change (reference standard)" in this audit. Justin surfaced during G7.5.a review that `NextTransactionDate` on the parent GC is a *rollup* the platform recomputes from open GTs' `TransactionDueDate` as payments post — so pointing the launcher input at it implies the value the user enters sticks, when it actually drifts. The Effective End Date-style intent is what the user is actually recording on a Simple leaf (the single expected payment IS the commitment's end).

**Applied:**
- Variable rename `dtNextTransactionDate → dtExpectedEndDate` (5 XML sites: screen field, `Assign_Pledge_Defaults` write, `formulaSimpleStartDateDisplay` × 3 refs, `formulaSimplePreviewText` description).
- Label: `When is the payment expected? (Expected End Date)`.
- helpText: rewritten to lead with the semantic ("commitment as a whole is expected to finish"), then explain the storage decision ("stable across time, unlike Next Transaction Date which the platform updates as payments post") and downstream reporting.
- Flow now writes BOTH `GC.ExpectedEndDate = dtExpectedEndDate` AND keeps the existing `GC.NextTransactionDate = dtExpectedEndDate` seed (pipeline reports still work at creation time; platform will overwrite `NextTransactionDate` on payment post, which is the intended behavior).
- `Assign_Pledge_Defaults` description updated with a forward reference to the parked follow-up.

**Parked follow-up (in wizard plan §Open follow-up):** convert Simple leaf to a GCS-backed shape (Custom period, single installment) so `NextTransactionDate` / `NextTransactionAmount` / `CurrentGiftCmtScheduleId` become platform-derived like every other commitment kind. Ship after G7.5 lands + fee-designation interlock — same launcher flow, same regression pass.

## Style rules applied

- **Choice-label separator:** em dash `—` (never spaced hyphen `-`). No trailing periods.
- **Parentheticals:** kept only when the API name is a report/formula landmark (OriginalAmount, TransactionDate, TransactionAmount, TransactionPeriod, TransactionInterval, Effective Start Date, Next Transaction Date, Expected Total Commitment Amount, Payment Method, Fulfillment Type, Formal Commitment Type, Match Eligible, Gift Commitment Category, Schedule Start Date, Match Ratio). Dropped elsewhere.
- **helpText:** every InputField gets one, one sentence, "what it means / when to use." Docstring-adjacent tone, not conversational.
- **Statement labels → questions** on radio/dropdown fields (matches the Pledge/Recurring/Scheduled screen family).
- **"mark the checkbox"** not "tick the checkbox."
- **API names in helpText:** replace with human names (`FQS_Match_Ratio__c` → "Match Ratio"). "PRG" is jargon — soften.
